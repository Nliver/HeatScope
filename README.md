# HeatScope

HeatScope 是一个面向官网、落地页和活动页的页面增长诊断与改版工作台。它把页面结构、热力图、点击数据、运营规则和多模型分析放进同一条可追溯流程，最终输出可直接预览的独立前端 HTML，并为上线后的同口径复盘保留证据链。

当前版本：`V0.5.6`

## 为什么做 HeatScope

页面优化不应只依赖视觉偏好，也不能把点击次数直接解释成转化、留存或因果提升。HeatScope 关注三件事：

- 让每条诊断结论都能回到页面证据、点击数据或运营规则；
- 让不同模型的判断和生成结果可以独立比较，而不是互相覆盖；
- 把“分析、改版、上线、复盘”连成一条可恢复、可审阅的闭环。

## 最新工作流

诊断任务采用四步线性 Wizard。后续步骤必须通过当前步骤的完成门禁才能解锁；回退修改上游证据会重置依赖它的分析和生成结果。

| 步骤 | 核心动作 | 完成条件 |
| --- | --- | --- |
| 1. 证据输入 | 填写 URL、目标、设备、受众、品牌变量和核心 CTA；导入热力图与 CSV/XLSX 点击数据；可抓取页面结构基线 | 必填证据通过校验并确认 |
| 2. 模型分析 | 本地规则引擎与已连接模型并行分析；在 Master-Detail 视图比较 P0/P1 问题；多选模型并实时合成改版 Prompt | 至少创建一个 HTML 生成 Job，且任一模型返回有效 HTML |
| 3. UI 结果 | 切换比较各模型的独立 HTML、优化点与状态；查看失败原因并对单个 Job 重试 | 至少选择或确认一个可用页面结果 |
| 4. 上线复盘 | 上传改版后的同口径行为数据，记录版本、结果判断和后续动作 | 提交复盘结论 |

### 模型生成不是“一败全堵”

每个已勾选模型对应一个独立 Job。`pending / running / streaming` 只表示任务仍在执行；只要任一 Job 成功返回并通过 HTML 校验，第 3 步就立即解锁。失败或超时任务不会阻塞成功结果，服务商错误、原始报错和单 Job 重试统一在第 3 步处理。

生成页面以隔离预览展示。预览前会移除脚本、导航地址、表单提交地址和内联事件，避免模型返回页面在工作台内执行跳转或提交操作；原始 HTML 仍可按需查看。

## 主要功能

### 诊断任务 `/diagnosis`

- 导入热力图图片以及 CSV/XLSX 页面点击数据；
- 标记 CTA、补充坐标，并让热力图与分析结果联动；
- 同时运行确定性的本地规则和多个模型分析；
- 按分析源比较严重度、依据、现状诊断和建议动作；
- 由模型选择、视觉输入、坐标和本地命中实时生成 Prompt；
- 派发多个独立 HTML Job，并在结果页处理混合成功、失败和运行中状态；
- 内置三个证据案例，用于快速体验输入与页面分析界面。

### 运营知识库 `/knowledge`

- 创建、编辑、启用和删除规则库及具体规则；
- 导入 `.docx`、`.md`、`.txt` 或 `.csv` 运营资料；
- 选择已连接模型，把分析案例归纳成可复用的运营方法论；
- 在确认后将原则、依据、动作、验证方式和护栏写入知识库；
- 启用的规则会作为后续诊断与 Prompt 合成的运营约束。

### 模型配置 `/models`

- 配置兼容 Responses API 或 Chat Completions 的模型服务；
- 管理 Base URL、模型 ID、推理强度、超时和启停状态；
- 先测试连接，再允许模型参与分析和 HTML 生成；
- 本地规则引擎始终可用，不依赖外部模型。

### 历史记录 `/history`

- 历史记录是冻结快照，不复用可编辑 Wizard 实例；
- 查看输入、证据、模型输出、采用蓝图和 HTML 结果；
- `mode=view` 全只读，`mode=review` 仅允许写入复盘结论；
- 诊断字段通过 `diagnosisChecksum` 校验不可变性；
- “复用数据重新分析”会创建新草稿，并把旧快照挂为对比基线；
- 复用时会比较历史与当前模型配置指纹，不展示明文 API Key。

## 快速开始

### 环境要求

- Node.js 20.9 或更高版本；
- npm；
- 外部模型不是浏览界面的必需条件，但模型分析和 HTML 生成需要至少一个连接成功的模型。

### 安装与开发

```bash
npm install
npm --prefix apps/web install
npm run dev
```

默认地址为 `http://127.0.0.1:3000`。若需要使用项目常用的 `4173` 端口：

```bash
npm run dev -- -- --hostname 127.0.0.1 --port 4173
```

### 构建与启动

```bash
npm run build
npm run start
```

### Vercel 部署

```bash
npm run deploy
```

部署命令以 `apps/web` 为项目根目录。生产 API、Worker、数据库与 Secret 服务的完整拓扑见 [生产部署与模型对比运行说明](docs/生产部署与模型对比运行说明.md)。

## 数据与安全边界

当前 `apps/web` 是可独立运行的工作台：工作区、模型配置、知识库、草稿和历史快照主要保存在浏览器 `localStorage`，模型请求由同源 Next.js API Route 转发。

- `.env.local`、API Key 和其他密钥禁止提交到仓库；
- 当前浏览器工作区适合本地或单用户验证，不应直接视为多人生产 Secret 方案；
- 浏览器存储有容量限制，大型历史快照可能被压缩保存；
- 点击数据只支持页面效率观察，没有曝光、结果事件或实验分流时，不输出因果结论；
- `apps/api`、`apps/worker`、`ent` 和 `internal` 是生产后端骨架，计划接入 PostgreSQL、Redis、Vault/KMS、异步任务和组织隔离。

## 仓库结构

```text
apps/
  web/       Next.js 工作台、页面路由与同源 API Route
  api/       Go API 服务骨架
  worker/    Go 异步任务服务骨架
ent/         Ent 数据模型与 Schema
internal/    模型网关、任务、对比、Outbox 与 Secret 领域模块
deploy/      本地生产拓扑与 Docker Compose
docs/
  product/   当前产品与架构文档
  archive/   历史方案归档
```

## 设计原则

- 证据优先：观察、判断、动作和验证口径必须能够对应；
- 结果独立：模型输出和 HTML Job 不互相覆盖，失败不阻塞成功结果；
- 人工决策：模型负责提供候选，最终采用、复盘和发布仍由用户确认；
- 快照不可变：历史诊断结果与可编辑草稿物理隔离；
- 谨慎归因：点击次数不替代转化率、留存率或因果证明。
